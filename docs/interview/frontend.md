### 说下 JavaScript 的事件循环机制

JavaScript 的事件循环，说白了就是一套协调代码执行的排队机制。因为 JavaScript 是单线程的，就像只有一个收银台，一次只能处理一件事，所以需要一种方式来决定同步代码、异步回调谁先谁后。主线程里有一个调用栈，可以理解成一个后进先出的盒子：所有同步函数调用都会压进去执行，后压入的先执行完弹出，就像叠盘子，最后放上去的最先拿走。当遇到 `setTimeout`、网络请求这类异步操作时，浏览器或 Node 环境会帮我们在背后处理，等时机到了，就把它们的回调扔进任务队列里排队。

任务队列其实分两种：宏任务和微任务。宏任务包括整段 `<script>` 代码块、`setTimeout`、`setInterval`、DOM 事件回调、老式 Ajax 的 `onreadystatechange` 等，它们是宿主环境提供的。微任务主要是 `Promise` 的 `.then`、`.catch`、`.finally` 里的回调，还有 `MutationObserver`，这些是 JS 引擎内部触发的。但要特别注意，不能单纯看 API 由谁发起：比如 `Fetch` 虽然是宿主提供的，但它返回 `Promise`，`.then` 里的回调是微任务，不是宏任务；老式 Ajax 用回调形式，那种回调就是宏任务。所以核心是看回调最终进入哪个队列：进宏任务队列的就是宏任务，进微任务队列的就是微任务。

事件循环的运转过程是：先执行最外层的宏任务（也就是整体代码），执行过程中碰到微任务就扔进微任务队列，碰到宏任务也扔进它的队列。当前宏任务执行完，调用栈清空后，事件循环会立刻把微任务队列里所有任务一口气全部拿出来执行完，直到微任务队列彻底清空。然后才会从宏任务队列里取出最靠前的一个宏任务执行，执行完再回过头来清空微任务队列，就这么一轮一轮反复。所以如果同时有 `setTimeout` 和 `Promise.then`，哪怕 `setTimeout` 延时是 0，也会先执行 `Promise` 的回调，因为它是微任务，优先级更高。

```TypeScript
console.log(1)
setTimeout(() => {
  console.log(2)
}, 0)
const p = new Promise((resolve, reject) => {
  console.log(3)
  resolve(1000)
  console.log(4)
})
p.then((data) => {
  console.log(data)
})
console.log(5)
```

拿上面的这段代码来拆解就非常清楚：一开始整体代码作为第一个宏任务执行，同步打印 `1`；然后遇到 `setTimeout`，把它的回调放进宏任务队列等 0 毫秒后触发；接着 `new Promise` 里的函数是同步执行的，所以立即打印 `3`，再调用 `resolve(1000)` 把状态改为成功，再打印 `4`；随后 `p.then` 把打印 data 的回调推进微任务队列；最后打印 `5`。到这里第一个宏任务执行完了，调用栈清空，事件循环先清空微任务队列，于是打印出 `1000`；微任务清空后，从宏任务队列里取出刚刚的 `setTimeout` 回调执行，打印 `2`。所以最终顺序就是 `1、3、4、5、1000、2`，正好体现了同步任务最先、微任务次之、宏任务最后的优先级规则。
